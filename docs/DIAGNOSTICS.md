# 诊断手册

排查任何问题都走同一条路：**先按现象查表，再按日志定位**。

- 第 1 章：按「现象」直接查（现场最快的入口）
- 第 2 章：串口日志逐条判读（确定根因）
- 第 3 章：两个必须知道的坑

> 日志全部走 `DebugLog.h` 的 `dbgLog()`：224 字节栈缓冲、零堆分配、
> USB CDC 非阻塞发送（缓冲区满直接丢，绝不阻塞主循环）。
> 115200 baud，**事件驱动**，正常静默运行。

# 1. 现象速查

## 屏幕

| 现象 | 处理 |
|---|---|
| 花屏 / 斜纹 / 撕裂 | 检查有无**无参** `SPI.begin()`（会把 SCLK 从 GPIO6 挪到 GPIO4）；脏矩形起始列是否为偶数 |
| 全白 / 全黑 | 量背光 **GPIO3** 是否为高；`initR(INITR_BLACKTAB)` 参数是否正确 |
| 帧率低 | 确认 `TFT_SPI_HZ` 为 20 MHz；看每帧变化面积是否超预算（见 [DISPLAY.md](DISPLAY.md)） |
| 开 WiFi 后屏幕卡住不动 | 看 `[GATE]` 行：**`fh` 一直涨** = 433 接收模块被 2.4 GHz 压得自激，属射频/摆位问题（挪远天线、加电源去耦）；**`fh=0`** = 只是偶发延迟，正常。机制见 [DISPLAY.md](DISPLAY.md) 第 3 节 |
| 屏幕偶尔卡一下，从机在不在都一样 | 查 `[HEALTH]` 的 `nz`：噪声突发被误判成帧。若 `nz` 大而 `ook` 小，是射频自激 |
| 目标颜色莫名变化 / 光点跳动 | 已由航迹跟踪消除；若仍出现，看是否为两个真实目标重叠 |
| 光点持续小幅抖动 | 传感器 10 Hz、屏幕 ~50 Hz，同一采样被重复画 5 帧。现有 EMA 平滑（系数 0.45）应已消除 |
| **右上角电量不显示** | GPIO0 是否接上分压中点、**中点的 100 nF 是否焊了**（没有它源阻抗 500 kΩ，读数偏低）。未采到电压时整块不画是设计行为，不是故障 |
| **电量一直显示 0%** | 电压越界（<1.5 V 或 >4.5 V）按 0% 显示：量一下 GPIO0 对地电压，正常应是电池电压的一半（满电约 2.1 V） |
| **电量显示明显偏高** | 正常路径不会这样。若读数系统性偏高，检查分压电阻是否等值（1MΩ/1MΩ） |

## 雷达

| 现象 | 处理 |
|---|---|
| **雷达不出数** | 接串口看 **[RADAR] ok= bad= raw=** 这一行（每 60 s 一行）：<br>`raw` 不涨 → 物理层没通（TX/RX 接反 / 没供电 / 传感器还在启动）<br>`raw` 涨但 `ok` 不涨 → 波特率不对或帧被截断<br>`ok` 涨但屏上无点 → 已进入算法层，与 UART 无关 |
| 读数不稳 | **雷达必须接 5V**，3.3V 供电会导致读数不稳甚至不出数 |
| 读数周期性跳 0 | 传感器漏采一次（该槽 x=y=0）；已有 350 ms 短时保持 |
| 角度偏一点 | 原按 2° 栅格对齐后查表；现为 2° 查表 + 线性插值，量化误差 ~0.02° |

## 433 无线 / 从机

| 现象 | 处理 |
|---|---|
| 某个防区偶发整轮丢失 | 可能是队列互挤（已修：`OOK_QUEUE_LEN` 16 槽 = 4 区 × 3 帧 + 余量） |
| **从机一上电就报有人 / 继电器自己吸合** | 雷达（RCWL-0515）和主板装在同一个壳里，上电后它把**从机自己**当目标。从机上电默认**待机**（不采样、继电器释放），单击 P3.2 才开启检测 |
| **上电瞬间继电器就吸合（还没按任何键）** | 8051 的 `TCON.IE0` 是硬件边沿锁存，**与 `EX0` 无关**。上电爬升期间 P3.2 上的任何下降沿都会被它锁存，`EA` 一开就立刻进 ISR → 待机态的边沿补救路径把毛刺当成一次按压 → 自动开检测。<br>修复：`App_Init()` 在 `EA = 1` **之前**补一句 `IE0 = 0;`（已修复）。<br>★ 注意这**不是**浮空电平抖动：准双向口 P3.2 在 latch=1 时约 30 kΩ 内部弱上拉，悬空读数是稳定高电平。IE0 锁存是唯一真实风险。 |
| **按 P3.2 没反应** | 按键语义**按状态分离**，**全部动作在松手那一拍完成，没有等待窗口**：待机单击（30~1200 ms）= 开检测；待机长按 1.5~5 s = 进配对；检测态单击或长按 = 关检测；配对态单击或长按 = 退出配对 |
| 待机单击后要等约 0.5 s 才真正报警 | 正常。开启后有 `APP_ARM_BLIND_MS` 500 ms 雷达基线盲区（留给人员撤离），盲区结束才重采基线 |
| 刚关掉检测后再按一下没反应 | 正常。退出检测 / 配对后有 `s_click_mute`（400 ms）静音，防止「快速连按两下」的第二下被当作待机单击把检测又打开。等半秒再按即可 |
| 配对完看不到「自动退出」提示 | 正常。433 对从机是**纯单向 TX**，从机收不到主机任何确认，无法感知「配对成功」。配对只有两条退出路径：20 s 超时自动回待机，或单击一下提前退出 |
| 按住 P3.2 时灯亮，松开就灭 | 正常。指示灯串在 P3.2 按键回路上（`VCC—LED—R—P3.2—按键—GND`），纯硬件，固件不参与。它只表示"手在按"，**不表示布防状态**；布防状态看主机屏幕或继电器 |
| 按键灯完全不亮 | 电阻太大或 LED 极性反。330Ω~1k 之间；若已用 330Ω 仍不亮，把 P3.2 对 VCC 量一下，正常应接近 3.3V（准双向口弱上拉） |
| 按键完全按不动 / 一直误动作 | 电阻 < 220Ω 时引脚电平可能抬不到能识别的高电平，或上拉被过载。换回 1k 验证 |
| **待机时防区闪离线** | 待机心跳 10 s，主机门限 45 s。若 433 链路丢帧成簇导致偶尔闪，把 `app.h` 的 `APP_STANDBY_HB_MS` 改小到 `5000u` |
| A 区一动 B 区就掉线 | 典型的**相位碰撞**：两台从机同时发，后一帧的前导被前一阵发的 SPI 推屏打掉。看四个防区的 `f=` 是否相差很大 |
| 从机反复重启 | `[HEALTH]` 的 `rst` 持续上涨 + `rbt` 很小。最常见：433 发射瞬间把 Vcc 拉塌导致欠压复位 |
| **开了检测之后很快自己又关了** | 布防态**不接受**「只有下降沿、没采到低电平」的事件作为关闭指令——那是 433 发射突发 / 继电器吸合的地弹毛刺，误关 = 漏报。**若仍复现**，看 `[HEALTH]` 的 `rst`：<br>`rst` 不涨 → 仍是干扰毛刺（查继电器续流二极管、P3.2 上的 RC 滤波）<br>`rst` 涨 + `rbt` 很小 → 是**欠压复位**（Vcc 被拉塌），属硬件，固件改不好 |
| **433 发射模组烧毁** | 固件侧已排除：`OOK_SendFrame()` 收尾即 `TX433_LOW()`，`OOK_Init()` 上电即拉低，`OOK_DelayUs` 有 `T0_GUARD_MAX` 有界守卫，占空比 ~3%~15%，无连续载波模式。**是硬件问题**，按可能性排序：<br>① **天线**（最常见）：没接 / 长度不对（λ/4 ≈ 17.3 cm）/ 接地差 → VSWR 极高 → 反射功率打回功放 → 功放管烧毁<br>② **继电器线圈没有续流二极管** → 吸合瞬间地弹 → 同时冲击 P3.2（误关）和模组供电（烧毁）<br>③ 模组额定电压高于实际供电，或电源带载不足<br>④ 电平不匹配：3.3 V 版模组接了 5 V 的 DATA 高电平会击穿输入 |
| 串口有 `[OOK]` 但防区一直离线闪 | **ID 不匹配**。对照开机日志 `[ZONE]  #0 id=` 和 `[OOK]` 行的 ID。换芯片/换板后 STC8 出厂唯一 ID 会变，必须重新配对 |
| 一帧都收不到，`nz` 很大 | 433 接收模块自激（干扰 / 天线差 / 供电脏）。`nz` ≈ 0 才是正常 |
| `ovf` 持续增长 | **帧是主机丢的**（RMT 环形缓冲溢出），与射频无关 |
| `crc` 一直涨 | 看 `[FAIL]` 直方图定位是哪道闸门（见第 2.5 节 `[FAIL]`） |

| 现象 | 处理 |
|---|---|
| 构建报 `intelhex` 找不到 | 用系统 Python 下的 `pio`，脚本已自动优先选可用的 |

# 2. 串口日志判读

每条都给出真实格式串（从 `src/master/master.ino` 直接复制）。

## 2.1 开机

```
=== HEARTBEAT v1.0.0 C3 ===
[BOOT] reset=%s raw=0x%02X(%s) heap=%lu
[ZONE] stored=%d
[ZONE]  #%d id=%s name=%s en=%d
[BOOT] loop WDT %s (5s)
[OK] %s
```

真实示例：

```
=== HEARTBEAT v1.0.0 C3 ===
[BOOT] reset=SW raw=0x03(SW) heap=265004
[ZONE] stored=1
[ZONE]  #0 id=F7:94:C6:19:19:CB:3D name=A en=1
[BOOT] loop WDT armed (5s)
[OK] RUNNING
```

### `[BOOT] reset=` —— 第一行就该看这个

现场说「死机了」之后重启，靠这一条就能把原因分到三类，**三者修法完全不同**：

| `reset=` | 含义 | 该查什么 |
|---|---|---|
| `SW` / `0x03` | 软件复位（`ESP.restart()`） | 正常：配网保存后、工厂复位后都会这样 |
| `BROWNOUT` / `0x0F` | **掉电复位** | 供电被拉垮。最常见：433 发射瞬间 Vcc 塌陷、USB 线太细、雷达 5V 与模块共用一路 |
| `TASK_WDT` / `0x0B` | **主看门狗** | 主循环被阻塞 5s 以上。查是否有新增的阻塞调用 |
| `PANIC` | 程序异常 | 看核心转储；常见是 `LoadStoreAlignment`（非对齐访存）或踩穿栈 |
| `0x15` | USB 串口（烧录后） | 正常：刚烧完就这行 |

### `[ZONE] stored=` —— 配不上对时的决定性证据

打印主机 EEPROM 里**已保存的**从机 ID。必须拿它和后面 `[OOK]` 行里从机
**实际发的** ID 逐字节对照：

- 一致 → 配对正常
- **不一致 → 主机根本不认这台从机**。换芯片 / 换整块板子后 STC8 的出厂
  唯一 ID 就变了，此时「防区永远离线、报警反复复位」，现场表现像「采样慢 /
  延时大 / 从机重启」，实际是没配对
- `stored=0` + `(empty - press PAIR on the slave)` → 从没配过对

> ⚠️ **只看到 `[OOK]` 行就以为收到了，是最容易踩的坑。** `[OOK]` 行是无条件
> 打印的（任何 ID 都打），而只有 ID 匹配才会更新防区。

### `[OK] RUNNING` / `[OK] NO DATA`

雷达 UART 是否在开机时探测到数据。`NO DATA` 不代表故障——本固件会把 UART
先起在 256000，之后传感器上电/复位还能接住，屏幕依然进雷达界面。
真正的判据是 `[RADAR]` 行。

## 2.2 收帧事件

```
[OOK] %02X:...:%02X flags=%02X seq=%u
[OOK] Already-known device seen during pairing
```

`[OOK]` 只在**首次见到某台设备**时打印（靠 `static s_logId[7]` 去重），
不是每帧都刷。所以日志里有这一行 = 射频链路和协议解码都是通的。

`flags` 位含义：

| 位 | 含义 |
|---|---|
| `0x01` | `OOK_FLAG_PRESENCE` 检测到人 |
| `0x08` | `OOK_FLAG_PAIRREQ` 从机主动请求配对 |
| `0x80` | `OOK_FLAG_BOOT` 从机刚重启（开机后前几帧置位，正常运行永不置位） |

`0x02` / `0x04` 是协议保留位（防拆 / 低电），从机目前从不置位。

## 2.3 每分钟健康日志（核心）

每 60 秒打印一组 7 行。**这是验证长期可靠性的唯一客观手段。**

```
[ZONE ] zn=%d act=%d
[ZONE ]  #%d id=%s name=%s en=%d on=%d f=%u age=%lums     ← 每个防区一行
[HEALTH] up=%lum heap=%lu min=%lu loop=%lums stk=%u tstk=%u ook=%lu crc=%lu nz=%lu ovf=%lu T=%uus rst=%u rbt=%lds wdt=%s did=%s
[GATE] fs=%lu fh=%lu
[RADAR] ok=%lu bad=%lu raw=%lu
[FAIL] f1=%u f2=%u f3=%u f4=%u f5=%u f6=%u f7=%u f8=%u f10=%u f11=%u
[FIXB] fixed=%lu wbit=%d wcnt=%u
```

### `[HEALTH]` —— 现场只需先看这三个数

| 字段 | 含义 | 正常值 |
|---|---|---|
| `heap` | 当前空闲堆 | ≥ 180000，且**不单调下跌** |
| `min` | 上电以来最低水位 | **等于 `heap` ⇒ 零泄漏**（稳态下两者应几乎相同） |
| `loop` | 主循环最坏耗时（本分钟） | 10–20 ms，必须远小于 5000（WDT） |
| `up` | 连续运行分钟数 | 递增；**变小说明重启过** |

其余字段：

| 字段 | 含义 | 判读 |
|---|---|---|
| `stk` | 主循环栈剩余（字节） | > 1500 安全；**< 500 立即加大** |
| `tstk` | tuya 任务栈剩余 | > 3000 安全；**< 500 改 `TUYA_TASK_STACK`** |
| `ook` | 累计有效帧 | 单调递增 |
| `crc` | 累计校验错 | 应长期接近 0（1% 以内属信道正常噪声） |
| `nz` | 噪声突发数 | **大而 `ook` 小** → 433 接收模块一直在自激，帧头立不起来，是射频问题，调固件无用；**小** → 接收机干净，问题在信号弱（功率/天线/距离）或从机发得不对 |
| `ovf` | RMT 环形缓冲溢出次数 | > 0 说明主机边沿都来不及读，**帧是主机丢的，与射频无关** |
| `T` | 单位时长估计（µs） | 设计值 350。明显偏离说明接收模块脉宽失真 |
| `rst` | 从机重启次数 | 见下表 |
| `rbt` | 距上次重启秒数 | `-1` = 从未观察到重启 |
| `wdt` | 看门狗状态 | 必须是 `armed`；`FAILED` 才是真故障 |
| `did` | 涂鸦 DeviceID | 未配网时为空 |

**`rst` / `rbt` 判读：**

| 现象 | 结论 |
|---|---|
| `rst` 不涨，`rbt` 很大或 `-1` | 从机运行正常，问题在射频 / 供电 |
| `rst` 持续上涨，`rbt` 很小 | **从机在反复重启**。最常见：433 发射瞬间把 Vcc 拉塌导致欠压复位 |
| `rst` 涨一次就停 | 只是上电启动，正常 |

> `rst` 用 `OOK_FLAG_BOOT` 做确定性判据，**不靠 seq 猜**。因为 seq 只有 8 位，
> 从机约 35~40 帧/分，6~7 分钟就回绕一次，「seq 变小」既可能是重启也可能是
> 回绕。判定窗口取 5s 会漏检（丢帧 85% 时相邻帧间隔常 > 5s），取 60s 又会把
> 正常回绕误报成重启——两个方案都实测被证伪过。

### `[ZONE ]` 行

| 字段 | 含义 |
|---|---|
| `zn` / `act` | 已配防区数 / 当前活动槽位 |
| `on` | 是否在线 |
| `f` | **该防区最近 60 秒收到多少有效帧** |
| `age` | 当前帧龄（距最近一帧成功解码多久） |

`f` 是「多防区链路质量」的唯一硬指标。**心跳为 2000 ms**，判读基准：

| `f` | 结论 |
|---|---|
| 45~60 | 链路正常（设计值 2000 ms/次 × 2 帧 = 60 帧/分） |
| 15~30 | 丢帧明显（天线 / 距离 / 供电 / 相位碰撞） |
| 0 | 该防区链路已断（或从未配对），看 `nz` / `age` 区分是射频问题还是 ID 不匹配 |

四个防区的 `f` **相差很大** = 典型的相位碰撞或某台天线差；
**四个都低** = 主机侧问题（接收模块 / 干扰 / 推屏门控）。

> ⚠️ **防区槽位必须逐个打印。** 这是踩过的真实误判：实际数据在 3 号槽
> （0/1/2 是空槽），而诊断只取了 `zoneAgeMs(0)` —— 空槽 `lastSeenMs` 恒为 0，
> 于是 `age` 天生等于开机时长，看起来像「从来没配对成功」，据此得出的
> 「ID 不匹配」结论完全是假的。多槽结构一律全打印，不要假设 0 号槽。

## 2.4 `[GATE]` —— 联网后才需要看

`fs` = 软强制放行次数，`fh` = 硬强制放行次数（本分钟）。

| 数值 | 含义 |
|---|---|
| `fs=0 fh=0` | 门控从来没卡住过（WiFi 关或干扰很轻），画面一直流畅 |
| `fs` 有小量、`fh=0` | 只是安静窗偶尔不满足，柔性强制已够，正常 |
| **`fh` 持续增长** | 433 接收模块被 2.4 GHz 压得**持续自激**——屏幕靠硬强制保活，属射频/摆位问题（挪远天线、加电源去耦），调固件无用 |

机制说明见 [DISPLAY.md](DISPLAY.md) 第 3 节「分级强制放行」。

## 2.5 `[RADAR]` —— 「雷达不出数」的第一个分叉点

| 字段 | 含义 |
|---|---|
| `raw` | UART1 累计收到的**字节数** |
| `ok` | 校验通过并解析成功的完整帧数 |
| `bad` | 帧头对上但帧尾不对的帧数 |

| 现象 | 结论 |
|---|---|
| `raw` 一直不涨 | **物理层没通**：TX/RX 接反、传感器没供电、传感器还在启动（LD2450 上电约 1 s） |
| `raw` 在涨、`ok` 不涨 | 波特率不对（本工程按 256000 探测）或帧被截断 |
| `bad` 明显增长 | 线路噪声，或波特率擦边（帧头对上、帧尾不对） |
| `ok` 在涨但屏幕上没点 | **已进入算法层**：看防区 / 跟踪门限，与 UART 无关 |

## 2.6 `[FAIL]` —— 丢帧到底丢在哪道闸门

解码器每道闸门失败时用 `_fail(code)` 记一次，每分钟打一张直方图。
**一次 60 秒就能给出确定答案，不必再猜：**

| 占比最高 | 根因 | 对策 |
|---|---|---|
| **F11** | 位判错了（段长都在合法窗口内，只是长短判反）。根因是接收机 AGC 在某几个位上把边沿拉偏 ~250 µs | 调 `OOK_BIT_MIN/MAX` **无用**（本来就没越界）。看 `[FIXB]` |
| F2 / F3 / F7 / F8 | 有段长越界 → 这才是窗口问题 | 扩 `OOK_BIT_MIN` / `OOK_BIT_MAX` |
| F5 | 两簇分不开 → 该帧形状整体坏 | 通常是干扰 / 推屏致盲 |
| F1 / F6 | 载荷段数不够 → 帧尾被帧间隔吞掉的比例变了 | 查帧间隙 / 从机发送节奏 |
| F4 | 有效样本太少 → 帧体大面积丢失 | 查射频 |
| F10 | 出现等长段 → 极可能是噪声凑出来的假帧 | 查 `nz` |

## 2.7 `[FIXB]` —— 单比特纠错成效

| 字段 | 含义 |
|---|---|
| `fixed` | 靠单比特纠错救回的帧数（说明纠错真在起作用，通信可靠性已实质提升） |
| `wbit` | 出错最集中的比特位 |
| `wcnt` | 该位出错的次数 |

若 `wbit` **长期固定在某一位**（尤其 79 号末位），说明该位的判定方法有
系统偏差（末位缺少配对段，只能靠全帧中点门限），应针对该位单独优化，
而不要整体调门限。

## 2.8 事件类日志

配对、工厂复位、按键等事件随时打印，不占用 60 秒节拍。

# 3. 两个必须知道的坑

**串口日志里不会出现任何 `[E]` 行。** `platformio.ini` 的
`-DCORE_DEBUG_LEVEL=0` 使 Arduino HAL 的 `log_e` / `log_w` / `log_i`
全部编译为空语句，所以像 `spiAttachMISO()` 那类无害但看着像故障的提示不会出现。
**若日志里真的冒出 `[E]`，那就是真故障，可以直接当报警看。**

**N4 模组用原生 USB，打开串口这个动作本身会让芯片复位**（DTR/RTS）。
想测真实连续运行时间，请用 `utils/serial_monitor.py`（已做 DTR/RTS 抑制
+ 自动重连），不要用串口助手直接点开。
